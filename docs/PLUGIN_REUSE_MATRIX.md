| --- | --- | --- | --- | --- |

## 为什么以前一直显示“0”

旧复用扫描只通过宿主 `AccountPool` 查找通用来源账号，无法识别这些插件独立的存储：Lingxi 使用私有 `state.json`，Loomy 额外使用桌面授权文件，ZCode Start Plan 使用单独 SQLite，WorkBuddy 的原 DSH 插件拥有自己的授权仓库。因此“0”不能用作“无账号”结论。

## RC.6 修复范围

- 新增按需运行的插件库存只读扫描；仅对固定的包和约定路径读取严格限长的授权记录元数据（为判断存在性可能在内存中读取原会话，不落盘、不输出）。SQLite 仅读取 id 和 enabled，不查询 credential 列。
- UI 对每个已安装插件显示紧凑摘要和授权记录计数。没有可读取账号时明确显示未核验或读取受限，而不是把插件路由当作已认证账号。
- 用不含 SID 的稳定摘要标识待核验候选。扫描不会自动导入、复制、修改、刷新、退出或签到，不会向云端发请求。
- 通用 DSH AccountPool 账号走既有迁移路径；原 Loomy 和 ZCode Start Plan 的私有账号走 MIT 来源包兼容迁移；Lingxi 需要独立驱动；WorkBuddy 加密私有凭据尚待验证。均须所有者逐账号确认，没有自动复制与删除。

## 后续必须通过的独立运行验收

为每种私有来源分别落实独立登录授权、会话续期、模型协议、模型目录、账号精确选择和有支持时的签到，执行：登录有效 → 原插件停止 → 重载 DSH → 自有 Provider 模型调用成功 → 刷新授权 → 签到结果由上游确认。未跑过的渠道不能标记为“迁移完成”或建议卸载原插件。

旧 Node 运行时可能缺少内置 `node:sqlite`。此时 ZCode 数据库扫描报告“来源读取受限”，并不会视为零账号；应核验 DSH 宿主实际 Node 版本，不能凭命令行 PATH 的 Node 版本推断。

ZCode Start Plan 的原代码许可证为 GPL-3.0-or-later；本 MIT 插件不直接复制、打包其 GPL 源码。Lingxi 当前已安装包缺少明确的 license 元数据，未确认许可证前也不照搬私有模块。

所有原插件的状态文件、数据库、官方桌面登录文件维持只读，保留原账号及原集成。
