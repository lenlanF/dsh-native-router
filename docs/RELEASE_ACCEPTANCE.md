## RC.25：13 渠道自有身份、余额、推理分层验收

- [逐渠道 E2E 能力矩阵](CHANNEL_E2E_MATRIX.md) 是目标清单。必须区分模拟官方接口通过与实际生产环境确认。
- 接管后本插件只调用自有凭据池下的渠道官方接口；禁止定时依赖原插件账户文件和缓存姓名。首次迁移仅复制合法公开资料作为临时回退。
- 不因模型目录、账号发现、旧插件鉴权或余额缓存就宣称可用。自有账号实际成功推理需要记录独立时间戳；模型可选也不代表推理成功。
- 一套跨渠道公开姓名与积分余额解析，拒绝编号昵称、无效单位及读取失败误标 0。旧 `sp_*` 引用不可直接作为独立接管。
- 未返回可核验远程账号事实、未能完成模型请求、token 已失效、没有续期或签到 API 时，需要分别展示失败原因和补齐对应渠道实现。

## RC.24：真正接管与独立运行的架构验收

- 运行态原插件资料读取为 0，扫描仅由用户动作触发；旧引用与自有账号的标签明显区分，停用原插件后自有账号模型/签到不受影响。

## RC.23：账号身份、今日历史、渠道标签一致性

- 每个来源账号的接管操作返回可显示的结果和安全错误状态，`already_owned` 被当作成功但「待云端核验」；已在配置中出现的账号可在下次预览显示已有接管记录，绝不直接宣称在线。
- 同名原插件 WorkBuddy、Loomy 保持宿主 Provider 独立运行，MIT 自有渠道包通过 `native-router-source-*` 重新提供全部 13 个自主登录与模型适配入口，不修改原插件的凭据和账号池。离线 Cordis 验证 13 个别名均已注册。
- 自包含单一 .tgz 包含固定 DSH 运行模块及间接依赖；构建器在 E:\Temp 中只从发布白名单复制源文件，安装后逐个 SHA256 校验打包内容，禁止包含用户凭据、日志和原始 MIT 开发包。
- 生产 DSH 直接扫码/网页新账号授权、账号迁移和完整签到能力仍需真实用户操作及相应远端确认。自动验收只证明安装、隔离路由与界面反馈，不宣称所有渠道已获得授权。

## RC.8 增量事实与未满足的正式验收

- WorkBuddy 本机私有授权：国内、国际各有 2 个候选；均可通过原 MIT vault 格式验证区域和身份，私有凭据只在用户逐账号同意时复制到 DSH Credentials。
- **真实上游模型验证**：国内/国际 WorkBuddy 模型目录 HTTP 200，原始记录 60/28；独立驱动分别使用 `deepseek-v4.1-flash` 生成 2 个字符正文，完成状态 `stop`。Lingxi 真实列出 11 个模型、`qwen3.8_flash` 生成 2 字符正文并正常结束，未向日志输出内容或令牌。
- **隔离/自动验收**：WorkBuddy 两区原文件移除后仍独立推理，刷新后的新凭据在重构驱动后依然可用；按账号签到必须服务端二次确认。原 MIT 渠道包全部 13 类来源，逐账号路由模拟 26 条账号不跨渠道/不回退其他账号。
- **仍未验收**：生产环境卸载原 WorkBuddy 插件后的长期续期、真实 WorkBuddy 签到、Lingxi 授权失效后的重新登录、全部 13 类渠道的各自真实账号调用、ZCode 云端/风控签入；禁止以模拟或目录 HTTP 200 替代这些结论。

**独立接管验收边界**：仅对兼容 DSH AccountPool 授权做逐账号所有者确认迁移，原 DSH Provider 不被替换；关闭原插件后须重新加载 DSH 并验证模型调用与签到才可声称独立可用。详见 [OWNED_CHANNEL_ADOPTION.md](OWNED_CHANNEL_ADOPTION.md)。

**RC.7 MIT 原生接管**：Loomy、ZCode Start Plan 的原私有账号，经用户逐条确认后转换为固定 MIT 多渠道包格式，在独立 DSH Credentials 与专属来源池持久化，建立 `own_loomy` 和 `own_zcode` 模型链。原插件停止/移除的离线模拟通过，但正式 DSH 中真机卸载、会话有效期、真实模型输出及签到仍须逐渠道验收，不以目录 HTTP 200 或模拟调用冒充全面上线。

**RC.6 私有插件发现**：新增 WorkBuddy、Lingxi、Loomy、ZCode Start Plan 的包安装与私有账号只读检测；独立数据库无法读取时明确显示受限。私有授权记录不复制、不冒充已认证账号。插件停用后仍能完成真实推理/签到的独立驱动，除此前已经验证的兼容 AccountPool 外仍未实现，不能作为本轮已验收成果。

**RC.4 双模式增补**（rc.5 保留）：模拟宿主的源码回归测试覆盖 DSH Provider 无账号委托推理、没有模型目录时手动导入、内置渠道授权与宿主同名 Provider 共存及专有账号池/凭据命名空间。内置来源的 13 种入口是总量，与宿主同名时以原插件为准，实际自主授权渠道数会减少；有独立逐账号签到实现的 9 种渠道仍需线上逐项验证。**尚未在当前正式 DSH 账号中做真实扫码、在线推理和签到。**

**CI 与真实磁盘隔离的区别**：GitHub Windows 托管虚拟机没有实际 E: 磁盘，通过 `SUBST` 映射的 E: 在 `realpathSync.native` 后仍属于其它盘符，按设计会被 `channelPackIsolationReason` 拒绝。公开 Windows CI 因此运行 28 个无需物理 E: 的合成测试文件；`tests/embedded-pack.test.mjs` 和 `tests/source-checkin-bridge.test.mjs` 两个涉及真正 E: 磁盘安全门禁的集成测试，必须在项目绑定的真实 E: 测试机执行完整 `npm test`。**不得通过降低插件的真实目录校验让 CI 通过**。Ubuntu CI 核对 Git LF、来源哈希及跨平台配置测试。两类验证各有适用范围，不能混为一谈。

## 稳定版 1.0.0 的**阻断关口**

1. **正式 DSH 版本和桌面 GUI 实测（需要审批）**：在已备份且允许操作的 DSH 实例中安装候选包，验证菜单加载、模型列表、账号状态、来源登录复用、签到页、重启/升级/卸载及原渠道不受影响。不能仅靠 VM 注册测试声称已兼容桌面 UI。
2. **真实渠道鉴权/登录态续期（需要审批）**：用户明确指定允许测试的各渠道和账号；逐一核验已登录可直接复用、登录失效与刷新、人工启停、扫码/授权等；不得外借、复制或记录 Token。来源包支持 13 个渠道入口 ≠ 所有渠道的真实在线认证均可用。
3. **每日签到在线核验（需要审批）**：用户批准的真实账号逐渠道验证状态查询、领取/签到、回查确认和多账号隔离；有 9 个来源具备每日活动代码 ≠ 9 个渠道当前均有可执行任务。保持默认停用。
4. **危险/不可回滚工具的真实宿主策略**：离线验证两个并发合成工具不重复；实际多进程重启、掉电、工具已执行但回执丢失、真实 Shell/文件/网络工具的强幂等性尚未证明。生产配置建议先关闭 `hostFailover.enabled`，在可恢复的业务任务中先验收。
5. **发布权限（需要审批）**：用户确认最终版本号、npm 组织/仓库及公开发布目标后，才允许 npm publish / Git push / GitHub Release 或覆盖正式 DSH；当前只能交付 `.tgz` 候选供用户批准安装。

## 运维与安装要求

- DSH Host Node.js 最低 **22.10.0**；额外进程、8326 网关、Windows 计划任务均不需要。源码版本的前端 UI 和认证 API 必须由 DSH Host 自带的 Connection 服务提供。
- 如需试装：对准经允许的测试 DSH，使用本项目 `dsh-native-router-1.0.0-rc.4.tgz` 作为本地插件包、由 DSH 现有插件安装方式装载，并在系统插件页核对已安装版本和前端页面。**未对任何生产 DSH 执行安装。**
- 插件配置默认不开启现有认证自动扫描、内置来源包自动加载、每日自动签到及宿主自动续跑；启用前请核对具体账号与模型链。
- 回滚操作：通过宿主 DSH 原生插件管理卸载本插件或恢复原版本，再还原部署前备份的本插件配置；此操作不应删除其他 DSH 渠道账号或原 Provider。
