# RC.94 全渠道免费活动真实覆盖推进与能力边界

## 目标
聚合路由优先使用现有已登录的独立免费会员账号、赠送额度和平台积分。操作顺序是：读取官方资格 → 仅对确实已完成且免费可领取的任务提交官方领取 → 读取官方任务状态 → 官方赠送额度／钱包或账单核实。任务存在不等于奖励已到账，模型免费也不等于存在每日签到。

## 代码交付

1. 修复 rc93 真实缺口：原本 `POST /activities/action run-channel` 只识别额外 `claimActivities`，忽略已经实现的十个 source daily 签到执行器。现在只要该渠道有真实 daily `checkIn` 或额外无感 API executor，即可手动执行；仍由原 checkinCenter 的精确账号/渠道、启停、回执和防重复约束。
2. 渠道活动目录分开 `valid`（官方资格确认但未入账）和 `completed`（官方账单或钱包增量可证明）的状态。不把官方奖励配置值当成实际到账，也不把充值、会员购买权益或模型次数冒充奖励。活动记录只保留账号匿名ID、活动名、官方数值、单位和公开完成时间；不含 Cookie／Bearer Token。
3. `src/channels/workbuddy-growth.mjs`：只查 CN 已完成任务和已抵达旅行礼物；绝不模拟做任务、抽奖、派出旅行、补签、创建内容、耗费积分或付费。真实领取使用精确账号哈希回执 + 官方 claimed 状态 + 积分钱包精确正增量。断流后的旧回执只核验不重复发。
4. `src/channels/doubao-upstream.mjs` 和 `doubao.mjs`：只对官方 `task_status=2` 且明确奖励量的任务/里程碑走 `item/reward/claim` 接口；先核验登录用户和赠送窗口，仅存在一个可独立比较的 `grant` 窗口才提交写请求，成功后再请求官方任务状态与独立额度窗口。动作为纯官方领奖 API，无生成/聊天任务。请求结果不确定时仅留持久回执，直到官方正增量完成对账。
5. 持久哈希回执扩展为限定 `workbuddy_growth_task_`, `workbuddy_growth_travel_`, `doubao_task_` 的 24 位散列种类，继承同账号／同凭据／同奖励状态防重规则；新平台任务代码及秘密不保存为明文。对于旧类型记录读取保持兼容。
6. 原独立账号的 `benefits` 公开元数据允许携带上述严格白名单的新类型及经截断处理的任务名称；豆包单位保持 **平台赠送额度**，而不是错误的 **积分**。所有渠道活动显示状态只有真实证据支持才出现。

## 安全与验收边界
- 一切测试使用合成私有凭据和本机模拟官方返回；此时 **不能** 宣称所有真实账号奖励已到账或全部免费活动已获真实 API 验证。运行中的生产 rc92 不会被自动覆盖，自动签到开关不会被私下打开。
- 缺少官方执行器、认证过期、官方返回风控/验证码、要求支付/生成/发送/任务实际完成、余额不可核对，都会如实禁止盲目写入，不把活动伪造成成功。
- `tests/workbuddy-growth-activities.test.mjs`、`tests/doubao-free-activities.test.mjs`、`tests/rc94-free-activities-coverage.test.mjs` 新增跨渠道官方权限模型、无感领取／重复保护／到账严格证明。
- 完整回归以本轮最终 `npm.cmd test`、Chrome 实际内嵌界面验收、隐私扫描、发行包检查及 GitHub Windows/Ubuntu CI 为准。
